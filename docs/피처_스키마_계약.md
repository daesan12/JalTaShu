# 피처 스키마 계약 — Spark(데이터) ↔ AI 인터페이스 확정본

> 데이터 담당 질문 6건에 대한 AI 담당 확정 답변. 이 문서가 코드의 기준이며, 변경은 양쪽 합의 후 이 문서부터 고친다.
> 공통 원칙: **학습 때 만든 피처와 서빙 때 만드는 피처는 같은 정의·같은 단위** (train/serve 일치). 모든 시각은 Asia/Seoul aware.

---

## 1. Spark Batch 최종 output schema (학습 테이블 `train_buckets`)

| 컬럼 | 타입 | 정의 |
|---|---|---|
| `station_id` | string | 대여소 ID (예: `ST0001`) |
| `bucket_start` | timestamp (tz-aware) | 15분 버킷 시작 시각 — 키. **물리적 저장 시간대는 UTC 또는 Asia/Seoul 허용** (동일한 절대 시각이어야 함). 단, 버킷 경계·월 구분·요일·시간 슬롯·장애 구간·학습/검증 분할은 **반드시 Asia/Seoul로 변환한 뒤 계산** (월별 파일 분할을 UTC로 자르면 KST 월 경계가 깨진다) |
| `rentals` | int | **라벨(λ)**: 이 버킷의 대여 건수. 0인 버킷도 행으로 존재해야 함 (0 채우기 필수) |
| `returns` | int | **라벨(μ)**: 이 버킷의 반납 건수 |
| `slot_of_day` | int | 0~95 (= hour×4 + minute÷15) |
| `weekday` | int | 0=월 ~ 6=일 |
| `holiday_type` | string | `none` / `major`(설·추석 연휴 포함) / `regular` / `substitute`(대체공휴일) / `workers_day`(5/1). **임시공휴일(예: 2025-01-27)은 `regular`로 확정** (2026-09-14 합의 — 양쪽 구현 동일) |
| `temperature` | float | °C |
| `rainfall_1h` | float | mm/h — 버킷이 속한 정시의 시간당 강수 |
| `minutes_since_rain` | int | 마지막 강수(≥1mm/h) 종료 후 경과 분. 상한 1440으로 클립. 비 오는 중 = 0. **기준점·결측 규칙은 §6 정의를 따른다 (2026-09-16 확정)** |
| `profile_rentals` | float | 프로파일 테이블(§5)에서 조인한 해당 station×weekday×slot 평균 대여 |
| `profile_returns` | float | 〃 평균 반납 |
| `delta_30m` | float | 직전 30분 순변화 (§2) — 결측이면 NaN 그대로 |
| `delta_60m` | float | 직전 60분 순변화 (§2) — 〃 |

- **0-fill 순서 (확정)**: ① 원본 누락 마스크 구간은 **행 자체를 생성하지 않는다** → ② 남은 정상 관측 구간에서만 아래 운영 구간 규칙으로 0-fill. 도시 전체 대여가 '일 단위 0건'인 날은 시스템 장애로 간주해 자동 편입한다.
- **누락 마스크 구간 (2026-09-14 확정 — 이벤트 공백 실측 기반, KST 반개구간 [start, end))**:
  - `[2024-05-21 00:00, 2024-06-01 00:00)` — 도시 전체 0건 11일 (교차 검증 중 발견된 미기록 장애)
  - `[2025-02-26 15:45, 2025-03-04 11:00)` — 시스템 장애. 마지막 이벤트 02-26 15:27, 재개 03-04 11:02 실측. **일 단위(02-26~03-03)가 아니라 정밀 시각 구간** — 02-26 오전 실데이터는 살리고, 03-04 00~11시를 0으로 채우지 않는다 (관측 없음 ≠ 수요 0)
  - `[2025-12-01 00:00, 2026-01-01 00:00)` — 2025-12 데이터 자체 부재 ('25년12월' 파일 = 2025-01 복제본)
- **0건 버킷 생성 범위 (확정)**: 전체 1,374곳 × 전체 기간이 아니라 **그 시점에 운영 중이던 대여소만**. 운영 구간 = 이력에서 해당 대여소의 [첫 등장일, 마지막 등장일] (대여·반납 통틀어). 구간 밖은 행을 만들지 않는다(관측 없음 ≠ 수요 0 — 섞으면 λ̂이 희석돼 고갈 위험을 과소평가). 구간 안의 긴 0건 공백은 그대로 0으로 유지(저수요 대여소의 정상 패턴). 현재 운영 여부는 대여소 마스터 API와 대조. §5 프로파일 평균도 동일 규칙 적용.
- 제안된 컬럼 중 `hour`·`weekday`는 `slot_of_day`·`weekday`로 대체(15분 해상도 유지), `station_profile`은 값 하나가 아니라 대여·반납 두 컬럼으로 분리.
- `current_bikes`는 **이 테이블에 없다** — λ̂·μ̂ 모델의 피처가 아니라 2층 수식의 s (서빙 시 실시간 API 값).
- 결측 값은 억지로 채우지 말고 NaN으로 남길 것 — LightGBM이 결측을 자체 처리한다.

## 2. delta 계산 정의 (통일)

**의미 정의: "직전 N분간 잔여 대수 순변화"** (반납 − 대여).

- 학습(이력): `delta_30m = 직전 30분 returns 합 − 직전 30분 rentals 합` — 버킷 경계 기준, 자기 버킷 미포함 (bucket_start 이전 30분)
- 서빙(스냅샷): `delta_30m = bikes(now) − bikes(now−30m)` — 45초 스냅샷에서 가장 가까운 시각 사용
- 알려진 차이: 서빙 쪽에는 **재배치 트럭 이동**이 섞인다(학습 이력에는 없음). 드문 이벤트라 수용하되, 캘리브레이션에서 이 피처가 문제를 일으키면 제외가 1차 대응. |delta| > 20은 재배치로 간주하고 NaN 처리(양쪽 동일 적용).
- 서빙 초기 등 이전 값이 없으면 NaN.

## 3. 15분 버킷 경계 (통일)

- **반개구간 [start, end)**, 정시 KST 기준: `08:00:00 ≤ t < 08:15:00` → 버킷 `08:00`
- 경계값 `08:15:00.000`은 **다음 버킷**(08:15)에 속한다.
- 구현은 양쪽 모두 `floor(minute / 15)` — 반올림·ceil 금지.
- 예측 시점이 버킷에 걸치는 보간(8:10 출발 → 08:00 버킷 1/3 + 08:15 버킷 2/3)은 AI 서빙 코드 책임.

## 4. 예측 지평 (확정)

- **1~15분, 1분 간격 15개** (2026-09-17 개정 — 경로 기능이 도보 ETA 분 그대로 조회하도록 백엔드와 합의. 최초 MVP 5/10/15의 '사이'를 같은 두 버킷의 내분점으로 채우는 것이라 추가 검증 불요). **15분 초과(30분~)는 스냅샷 백테스트로 지평별 오차를 확인한 뒤 추가 여부 결정.**
- 예측 테이블·캐시는 지평을 **키의 일부**로 둔다 (`pred:{station_id}:{horizon_min}`) — 30분 추가가 스키마 변경이 아니라 키 하나 추가가 되도록.
- 지평은 별도 모델이 아니라 15분 학습 λ̂·μ̂의 율(rate) 스케일링으로 계산 (포아송 시간 가법성).

## 5. 대여소 프로파일 (역할 분담)

- **Spark Batch가 만든다.** 산출물: 별도 Parquet 테이블 `station_profile`
  - 스키마: `station_id, weekday, slot_of_day, avg_rentals(float), avg_returns(float)` (~1,374×7×96 ≈ 92만 행)
- ⚠ **누출 방지**: 프로파일 평균은 **학습 구간 데이터로만** 계산한다 (검증 구간 포함 금지). 구간 경계는 학습/검증 분할과 동일하게 데이터 담당이 파라미터로 받게 만들 것.
- AI 쪽은 이 테이블을 학습 시 조인하고, 서빙 시에도 같은 테이블을 로드해 사용 (서빙 재계산 없음).
- **신규 대여소(프로파일 결측) 처리 확정**: 학습 구간에 없던 대여소(검증 기간 10곳·51,072행 확인)는 **행 유지 + profile 컬럼 NaN 그대로** (LightGBM 결측 분기). 행 삭제·대체값 주입 금지 — 서빙에서도 신규 대여소는 NaN으로 추론(train/serve 일치). 평가는 프로파일 보유/신규 두 그룹 분리 집계(콜드스타트 한계 수치로 발표 활용).

## 6. 날씨 피처 단위·시간 기준 (통일)

| 항목 | 확정 |
|---|---|
| temperature | **°C, float** (Open-Meteo `temperature_2m` = 기상청 실황 `T1H`, 둘 다 °C — 변환 불필요) |
| rainfall_1h | **mm/h, float** (Open-Meteo hourly `precipitation` = 기상청 `RN1`, 둘 다 mm — 변환 불필요) |
| 사용 API | 기상청 단기예보 조회서비스(15084084) **초단기실황 `getUltraSrtNcst`** — 정시(H:00) 관측값을 H:40경 발표. 항목 T1H(기온)·RN1(1시간 강수). (예보 도입 시 초단기예보 `getUltraSrtFcst`, 매시 45분경) |
| 시간 기준 (**발표 지연 정렬 — 학습·서빙 동일**) | `weather_available(t) = obs(H) if t ≥ H:40 else obs(H−1)` — 시점 t에 실제로 발표돼 있던 관측값만 사용. 학습도 아카이브 관측을 이 규칙으로 시프트해서 붙인다(정시 값 단순 브로드캐스트 금지 — train/serve 불일치 원인). `minutes_since_rain`도 available 기준으로 파생 |
| `minutes_since_rain` 정의 (**2026-09-16 확정 — 실제 학습 Parquet 표본 검증 기준**) | 발표 지연이 적용된 15분 버킷 기준으로 계산한다. ① available 강수 ≥ 1mm/h인 버킷 = 0 ② 아니면 **마지막으로 강수가 available이던 15분 버킷 시작 시각**부터의 경과 분 (관측 정시 obs_time 기준이 아님) ③ 상한 1440 ④ **강수 결측(ffill 3시간 초과 NaN)은 '비 아님'으로 취급**하고 경과 분을 계속 센다 ⑤ 이력 내 강수가 없으면 이력 ≥ 1440분일 때 1440, 미만이면 NaN. 예: 08시 관측 2.7mm, 09시 관측 무강수 → 08:45~09:30 버킷 = 0, 09:45 = 15, 10:00 = 30, 10:15 = 45. **근거**: 43개월 `train_buckets`를 생성한 원본 Spark 배치 코드는 저장소에 없어 구현식을 직접 확인할 수 없었고, 모델이 학습한 실제 Parquet 값(2026-01-10 등 표본)을 양쪽 합의로 기준 삼았다. 구현: `features.last_rainy_bucket_start()`, 검증: `tests/test_train_serve_parity.py` |
| 다음 버킷 행 | 예측 시점 t까지 발표된 값만 — 현재 버킷 행과 다음 버킷 행이 같은 날씨 값을 공유하는 것이 정상. 미래 관측값은 어떤 행에도 금지 |
| 결측 처리 | 직전 값 유지(ffill) 최대 3시간, 그 이상은 NaN |
| 소스 정합성 (기상청↔Open-Meteo) | Open-Meteo 쿼리에 **`timezone=Asia/Seoul` 필수**(기본 UTC — 최다 사고 지점). 강수는 양쪽 다 "직전 1시간 누적, 정시 타임스탬프" 규약, 기온은 정시 순간값. 기상청 실황 로깅 시작 후 **겹침 기간 시간별 조인으로 실측 대조**(상관·강수 유무 일치율)가 최종 검증 |
| '비 안 옴' 기준 | **시간당 1mm 미만** (EDA 분석 기준과 동일 — minutes_since_rain 계산에도 이 기준 사용) |

## 7. 학습 / 검증 분할 (확정)

- **학습**: `bucket_start < 2026-01-01 00:00 KST` — 사용 월은 **실제 대여일시 기준 월별 행수 히스토그램으로 확정** (파일명 기준 "41개월"은 명목치. '25년12월' 파일은 실제 2025-01 데이터로 확인 — 정상 2025-12 존재 여부는 히스토그램이 판정. 없으면 학습이 한 달 얇아질 뿐, 경계는 불변)
- **검증**: `bucket_start ≥ 2026-01-01 00:00 KST` (2026-01 ~ 2026-03, 3개월)
- **dedupe 키 (2026-09-14 개정)**: `(자전거번호, 대여일시, 대여대여소, 반납일시, 반납대여소)` **완전 행 5키** — 파일 내·파일 간 모두 적용. ⚠ 3키(자전거·대여일시·대여소)로 지우면 안 됨: 같은 시각·같은 대여소에서 시작했지만 반납이 다른 실제 여정 쌍('0분 자기반납 + 진짜 여정', 22년08월에 470건)이 존재해 진짜 반납 기록이 임의로 소실된다
- **데이터 종료 시점**: `2026-04-01 00:00 KST` — 이후 이벤트(3월 말 대여의 4월 꼬리 반납 포함)는 불완전한 기간 밖 데이터로 명시적 제외. canonical↔zero_filled 등 파이프라인 내부 대조에도 같은 종료 시점을 적용할 것
- `station_profile` 계산 기간 = 학습 구간과 동일 (~2025-12-31)
- 검증 초입의 delta 피처가 학습 구간의 과거를 참조하는 것은 허용 (누출은 미래 참조만) — 경계 행 버리지 말 것
- 알려진 한계: 검증이 겨울~초봄에 치우침 → 여름 성능은 가을 스냅샷 백테스트가 보완 (발표 프레임: "겨울 검증 + 가을 실측 캘리브레이션")

## 8. 서빙 계산 규칙 (매분 배치 추론)

- **delta 서빙 재현**: `delta_Nm(t) = bikes(t 직전 스냅샷) − bikes(t−N분 직전 스냅샷)`. 목표 시각 ±3분 내 스냅샷 없으면 NaN. |delta|>20 → NaN(재배치). 수집기 기동 후 첫 60분 NaN. NaN은 채우지 않는다.
  - 재현성 검증(스냅샷 1주 후): 학습 delta 분포(시간대별 평균·분산) vs 서빙 delta 분포 대조. 크게 어긋나면 delta 피처 제외가 1차 대응.
- **지평 계산**: 별도 모델 없음. `λ_total(t,h) = Σ_b λ̂(b 피처) × (b와 [t,t+h] 겹침 분 / 15)` — 버킷 겹침 시간 비례 가중합 (포아송 시간 가법성). μ 동일. 이후 `예상 잔여 = s + μ_total − λ_total`, 고갈 확률 = Skellam 꼬리 `P(X−Y ≥ s)` × **보정계수 1.25**(단일값, 전 지평·전 대여소, `config.TAIL_CORRECTION`; [0,1] 클립). s ≤ 0이면 1. 계수는 2026-09-17 스냅샷 캘리브레이션(9/9~9/16, 결정 구간 s≥1)에서 실측/예측 1.12~1.34배의 낙관 편향을 메우는 Brier 최소값(지평별 1.20~1.35의 중앙값)으로 확정 — 데이터 추가 시 재확인.
- **배치 구성**: 대여소당 현재+다음 버킷 피처 행 2개(30분 지평 도입 시 3개) → predict 1회 → 5/10/15분은 산수로 도출. 매분 1,374×2 = 2,748행.

### 검수 체크 (양쪽 코드 완성 후)

1. 같은 하루를 골라 Spark 산출 버킷 수 = **그 날짜에 운영 중이던 대여소 수 × 96** 인지 (0 채우기 + 운영 구간 판정 동시 확인; 날짜별 운영 대여소 수가 1,374를 향해 대체로 증가하는지도 함께 볼 것)
2. 임의 대여소 3곳의 `delta_30m`을 수동 계산과 대조
3. 학습 테이블과 서빙 피처 벡터를 같은 시각으로 만들어 컬럼별 값 비교 (train/serve 일치 테스트) — `tashu-ai/tests/test_train_serve_parity.py`. 이 검수로 `minutes_since_rain` 기준점 불일치를 발견해 §6 정의를 확정함 (2026-09-16)
4. 누락 마스크 구간의 `train_buckets` 행수 = 0 확인 + "도시 전체 일 단위 0건" 날짜 목록이 마스크와 일치하는지 대조 (불일치 = 새 장애 구간 발견)
5. 실제 대여일시 기준 월별 행수 히스토그램 공유 → 사용 월 최종 확정 (파일명 불신)

### 확정된 비(非)피처

- `is_weekend` 추가하지 않음 — weekday의 함수(정보량 0), 트리가 `weekday ≥ 5` 분할을 스스로 학습. 파생 피처는 트리가 만들 수 없는 것에만(연속값 변환·외부 정보 결합).
